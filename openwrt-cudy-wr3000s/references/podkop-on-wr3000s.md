# Podkop на Cudy WR3000S v1

## Область документа

Официальная страница OpenWrt подтверждает аппаратную платформу, память, порты и поддержку системы, но не тестирует Podkop. Рекомендации ниже являются эксплуатационным профилем для 256 МБ RAM и двухъядерного MT7981, а не гарантией производительности.

## Возможности Podkop на WR3000S

Роутер подходит для:

- выборочной маршрутизации доменов и устройств;
- VLESS/Reality, Shadowsocks, Trojan и других outbound sing-box;
- WireGuard/AWG/OpenVPN через VPN-интерфейсы;
- FakeIP и DNS-политик;
- нескольких VLAN с разными правилами;
- полного проксирования выбранных устройств по статическому IP.

Ограничения:

- 256 МБ RAM требуют умеренного числа rule-set и служб;
- нет USB/extroot для простого расширения хранилища;
- внешние порты ограничены 1 Гбит/с;
- тяжёлое шифрование, SQM и сложные правила одновременно могут упереться в CPU.

## Рекомендации по sing-box

1. Использовать один основной экземпляр sing-box, управляемый Podkop.
2. Предпочитать штатную ссылку подключения, если Podkop её принимает.
3. Для VLESS/Reality проверять:
   - `server` и `port`;
   - UUID;
   - `flow`;
   - TLS `server_name`;
   - fingerprint;
   - Reality `public_key` и `short_id`.
4. Никогда не помещать private key сервера Reality в клиентскую конфигурацию.
5. Не редактировать сгенерированный JSON как основной способ настройки: изменения могут быть перезаписаны.
6. Ограничивать подробное логирование при нормальной работе.
7. Добавлять по одному outbound/section и проверять результат.

Для устойчивости сначала добиться работы одного соединения без сложных списков, затем добавлять routing policy.

## Рекомендации по FakeIP

Базовая схема:

```text
клиент
  -> dnsmasq роутера:53
  -> sing-box 127.0.0.42:53
  -> upstream DNS
  -> FakeIP 198.18.0.0/15 для доменов из прокси-списков
  -> nftables/tproxy
  -> выбранный outbound
```

Условия работы:

- клиент использует роутер как DNS и default gateway;
- nftables и перехват Podkop активны;
- Secure DNS/Private DNS клиента не обходит роутер;
- адресный диапазон `198.18.0.0/15` не используется локальной сетью;
- DNS и routing rules согласованы.

Не добавлять статические маршруты к FakeIP как замену штатному перехвату Podkop.

## Настройки DNS

Рекомендуемый базовый вариант:

- dnsmasq слушает LAN на порту 53;
- запросы Podkop направляются в sing-box на `127.0.0.42:53`;
- upstream использует DoH/DoT или UDP в соответствии с моделью угроз;
- для upstream по hostname задан bootstrap DNS;
- клиенты получают адрес роутера как DNS через DHCP.

Не включать `Dont Touch My DHCP`, если dnsmasq не настроен вручную. Не занимать `127.0.0.42` сторонним DNS-сервисом.

При использовании AdGuard Home заранее выбрать цепочку:

```text
клиент -> AdGuard Home -> Podkop/sing-box
```

или другую документированную схему. Не запускать два резолвера на одном адресе и порту.

IPv6 не отключать автоматически. Сначала определить, должен ли IPv6 идти direct, через поддерживаемый outbound или блокироваться осознанным правилом.

## Маршрутизация устройств

Сначала описать политику:

| Источник | Назначение | Действие | Outbound | DNS |
|---|---|---|---|---|
| trusted LAN | выбранные домены | proxy | VLESS/Reality | FakeIP |
| IoT VLAN | обновления производителя | direct/proxy по списку | выбранный | router DNS |
| guest VLAN | интернет | ограниченная политика | direct/proxy | router DNS |
| отдельный хост | весь трафик | Fully Routed IP | VPN/proxy | router DNS |

Практика:

1. Закрепить DHCP lease для устройств с политикой по IP.
2. Для полного туннелирования использовать Fully Routed IPs.
3. Для сервисов использовать минимальные доменные/IP-списки.
4. Не включать одновременно перекрывающиеся крупные региональные наборы.
5. Не использовать `Route Allowed IPs 0.0.0.0/0`, если нужен split tunneling.
6. VLAN isolation настраивать firewall, а не Podkop.

## Рекомендации для устойчивого доступа

- Иметь минимум два независимых outbound, если критична доступность.
- Для нескольких VLESS-серверов использовать Selector или URLTest после проверки каждого соединения отдельно.
- Не смешивать в одной итерации смену DNS, tunnel protocol и VLAN.
- Сохранять прямой доступ к панели роутера и локальным подсетям через Exclusion.
- Исключить адреса прокси-серверов из маршрутизации через сам прокси, чтобы избежать петли.
- Проверять MTU для туннелей при зависании крупных загрузок.
- Использовать NTP до запуска TLS-зависимых соединений.

## Практические советы по производительности

- Измерять WAN напрямую до включения Podkop, затем с одним outbound.
- Проверять загрузку обоих ядер через `top`/`htop`.
- Не совмещать максимальный SQM, тяжёлый VPN, DPI-подобные правила и подробные логи без теста.
- Сокращать rule-set до реально нужных.
- Отключать отладочные логи после диагностики.
- Контролировать память:

  ```sh
  free -m
  top
  logread | tail -n 100
  ```

- Контролировать размер overlay:

  ```sh
  df -h
  opkg list-installed
  ```

- Для теста пропускной способности использовать локальный `iperf3`, а не только браузерный speed test.
- При нехватке ресурсов перенести AdGuard Home, мониторинг и серверные приложения на отдельный домашний сервер, оставив роутеру маршрутизацию.

## Проверка после настройки

Проверить:

1. Клиент получает DNS роутера.
2. Домен из proxy-list возвращает FakeIP, если так задумано.
3. Dashboard/YACD показывает нужный outbound.
4. Счётчики nftables растут.
5. Локальные адреса и LuCI не уходят в прокси.
6. После перезагрузки Podkop и sing-box стартуют без OOM.
7. WAN и Wi-Fi сохраняют ожидаемую скорость и задержку.
